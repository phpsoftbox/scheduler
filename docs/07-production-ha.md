# Production и HA

## Два разных вида защиты

`withoutOverlapping()` и `onOneServer()` дополняют друг друга, но отвечают на
разные вопросы.

`withoutOverlapping(ttl)` удерживает lock, пока задача выполняется. После успешного
синхронного выполнения lock снимается. У queued-задачи он передаётся в payload и
снимается обработчиком очереди. Это защищает долгую задачу от запуска поверх уже
работающего экземпляра.

`onOneServer(ttl)` создаёт lease для конкретной due-минуты и не снимает его после
выполнения. Поэтому две реплики не выполнят одну быструю задачу дважды в одном
окне:

```php
$scheduler->run(RebuildReport::class, 'reports:rebuild')
    ->dailyAt('03:15')
    ->onOneServer()
    ->withoutOverlapping(3600);
```

TTL `onOneServer()` должен быть больше максимального расхождения времени старта
реплик и интервала проверки расписания. При стандартной минутной проверке значение
по умолчанию 120 секунд перекрывает всё due-window.

## Почему одного PSR-16 недостаточно

PSR-16 определяет `get()`, `set()` и `delete()`, но не определяет атомарные
add-if-absent и compare-and-delete. Последовательность `get()` → `set()` имеет race:
две реплики могут одновременно увидеть пустой ключ и обе считать lock своим.

`Psr16ScheduleLockStore` сохранён как совместимый fallback для одного процесса.
Он честно сообщает `isAtomic() === false`, поэтому `onOneServer()` с ним завершится
ошибкой конфигурации, записанной в `ScheduleResult`. Это не позволяет случайно
выдать single-process cache за HA-защиту.

Для Redis доступен атомарный адаптер:

```php
use PhpSoftBox\Scheduler\Lock\RedisScheduleLockStore;
use PhpSoftBox\Scheduler\Scheduler;

$locks = new RedisScheduleLockStore($redis, prefix: 'my_app:scheduler:');
$scheduler = new Scheduler(lockStore: $locks);
```

Захват использует Redis `SET NX EX`, снятие — Lua compare-and-delete. Исходный
owner token не может снять lock, который уже истёк и был получен другим процессом.
Для SQL или другого общего storage реализуйте тот же небольшой
`ScheduleLockStoreInterface`; обе операции должны быть атомарными на стороне
хранилища, а не собираться из отдельных read/write запросов.

## Ошибки и наблюдаемость

Вызывайте `dispatchResults()` и передавайте результаты в логирование/метрики.
`failed` содержит исходный `Throwable`, а skip-outcome позволяет отличить нормальную
работу lease от фактического запуска. Ошибка одной задачи не мешает следующим.

Timeout нельзя безопасно реализовать вокруг произвольного PHP-callable внутри того
же процесса: прерывание может оставить ресурсы и транзакции в неопределённом
состоянии. Задачи, которым нужны жёсткие timeout, retry/backoff или принудительное
завершение, следует отправлять через `onQueue()` и задавать эту execution policy в
изолированном queue worker. Scheduler отвечает за расписание и выдачу job, а не за
управление жизненным циклом чужого процесса.

## Clock и worker

`Scheduler` принимает PSR-20 `ClockInterface`; `ScheduleWorker` также принимает
его необязательным последним аргументом. В тестах передавайте frozen/mutable clock,
чтобы проверять due-window без зависимости от системного времени. В production
используется системный clock. На нескольких узлах всё равно необходима штатная
синхронизация времени.

## Развёртывание

`schedule:work` загружает schedule-файлы один раз при старте. После релиза или
изменения конфигурации worker нужно перезапустить. Один экземпляр может работать с
PSR-16 fallback; несколько экземпляров разрешены только после подключения общего
атомарного lock store для всех задач, помеченных `onOneServer()`.
